# chekmate

Телеграм-бот, который считает **личную инфляцию** по кассовым чекам.

**Попробовать: [@chekmate1_bot](https://t.me/chekmate1_bot)** — живой экземпляр,
поднятый для проверки на настоящих чеках. Он может быть недоступен: работает
на одной виртуальной машине без резервирования, и я останавливаю его во время
работ. Если бот молчит — поднимите свой, это делается одной командой
`docker compose up -d`.

Учёт расходов обычно останавливается на сумме покупки: «магазин, 3 450 ₽».
В чеке же лежат позиции — а значит, можно считать не только траты, но и цены:
что подорожало, на сколько и в какой категории.

```
📊 Ваша инфляция за 3 мес.: +7,4%
   Считано по 47 товарам вашей постоянной корзины.

   Молочное        +14,2%
   Сладости         +9,8%
   Овощи            −3,4%

   Сильнее всего подорожало:
   · масло сливочное: 1 240,00 ₽ → 1 490,00 ₽ (+20,2%)
```

## Что умеет

**Принимает чек одним действием** — фото QR-кода. Сумма и дата берутся из
самого кода, состав — из сервиса проверки чеков по фискальным реквизитам.
Можно и текстом: `молоко 930мл 89`, при желании с магазином — `@Лента`.

**Опознаёт товары между магазинами.** Строка `МОЛ.ПРОСТОКВ.3,2% 930МЛ` из
одного чека и `Молоко Простоквашино 3.2 930г` из другого сводятся к одному
товару. Если бот не уверен — спрашивает кнопкой и запоминает ответ навсегда.

**Раскладывает по 18 категориям на уровне товара, а не магазина.** Покупка
в «Магните» распадается на еду, химию и алкоголь — как оно и есть.

**Показывает детализацию по кнопкам.** Отчёт → категория → товар → история
цены; история покупок → чек → его позиции. Сообщение переписывается на месте,
переписка не засоряется. Период переключается там же: неделя, месяц, прошлый
месяц, всё время.

| Команда | Что делает |
|---|---|
| фото QR | добавить чек |
| `/report` | расходы по категориям, сравнение с прошлым периодом |
| `/inflation [месяцев]` | индекс цен по своей корзине |
| `/top` | что подорожало сильнее всего |
| `/price молоко` | история цены товара |
| `/rule сгущенка sweets` | своё правило категории с пересчётом уже купленного |

В групповом чате бот реагирует только на команды, фото и ответы себе —
семейный бюджет ведётся общий, переписка не засоряется.

## Запуск

```bash
cp .env.example .env      # впишите BOT_TOKEN и RECEIPT_API_TOKEN
make up                   # поднимает PostgreSQL
make test                 # тесты, включая интеграционные
go run ./cmd/bot          # миграции применятся сами
```

`make reset` пересоздаёт базу с нуля — нужен, если правились уже применённые
миграции. До первого релиза это допустимо, после — изменения вносятся только
новой миграцией.

## Ключи и настройки

Все настройки — переменные окружения, шаблон лежит в `.env.example`. Копия
`.env` в репозиторий не попадает.

| Переменная | Зачем |
|---|---|
| `BOT_TOKEN` | токен бота от @BotFather, обязателен |
| `DATABASE_URL` | подключение к PostgreSQL, обязательно |
| `RECEIPT_API_TOKEN` | ключ сервиса, отдающего состав чека |
| `RECEIPT_API_URL` | адрес этого сервиса |
| `TELEGRAM_PROXY` | прокси, если Telegram недоступен напрямую |
| `TIMEZONE`, `LOG_LEVEL`, `HTTP_ADDR` | необязательные |

Без `RECEIPT_API_TOKEN` бот работает, но видит в чеке только сумму и дату:
позиции разбирать будет нечего, и вся аналитика по ценам останется пустой.

Формат ответа стороннего сервиса описан в одном месте —
`internal/enrich/response.go`. Если сервис изменит структуру или понадобится
другой источник, правится только этот файл.

Если `api.telegram.org` недоступен напрямую, задайте адрес прокси —
поддерживаются `http://`, `https://` и `socks5://`:

```bash
TELEGRAM_PROXY=socks5://user:pass@1.2.3.4:1080
```

## Как это устроено

```
cmd/bot          точка входа: конфиг, зависимости, корректное завершение
cmd/coverage     замер точности категоризации на размеченных строках
internal/
  domain         Money, Quantity, Receipt — ядро без внешних зависимостей
  qr             декодирование QR со снимка и разбор фискальной строки
  enrich         состав чека по фискальным реквизитам
  normalize      приведение названий товаров к каноническому виду
  catalog        сопоставление с товарами и категоризация
  analytics      отчёты, индекс цен, границы периодов
  service        сценарии: разобрать, сопоставить, сохранить
  bot            приём сообщений, клавиатуры и тексты
  storage        схема, миграции, репозитории на pgx
  httpsrv        healthz, readyz, метрики
```

Зависимости направлены внутрь: `domain` не знает ни про Telegram, ни про базу;
`bot` не содержит логики; `service` не знает, откуда пришло сообщение.

## Принятые решения

**Не зависим от одного источника.** Сумма и дата берутся прямо из QR-кода
чека — этого достаточно, чтобы учесть трату. Получение состава вынесено за
интерфейс `Enricher`: когда источник недоступен или ещё не знает чек, трата
всё равно сохраняется.

**Деньги — целые копейки, количество — тысячные доли базовой единицы.**
Накопление сотен позиций во `float64` даёт видимую пользователю ошибку, после
которой «итого» перестаёт сходиться с чеком.

**Цена хранится за базовую единицу — ₽/кг, ₽/л, ₽/шт.** Из этого бесплатно
получается детекция шринкфляции: пачка, ужавшаяся с 400 г до 380 г при той же
цене, автоматически становится подорожанием.

**Часовой пояс передаётся явно.** Время на кассе местное и записано без зоны,
а сервер живёт в UTC. Без явной зоны ночные покупки уезжали бы в соседние
сутки и ломали границы отчётных периодов.

**Даты собираются вручную.** `Format("2 января")` в Go печатает январь круглый
год: русских месяцев в стандартной библиотеке нет.

**Индекс цен считается по сопоставимым товарам с весами по расходам.** Это
индекс Ласпейреса: объёмы зафиксированы, поэтому рост расходов из-за того, что
вы стали больше покупать, инфляцией не считается. Цена берётся медианная —
иначе одна покупка по акции обваливала бы индекс. В расчёт входят только
товары, купленные хотя бы трижды в каждом периоде.

**Незавершённый месяц сравнивается с равным отрезком предыдущего.** Иначе
шестого числа отчёт показывал бы обвал расходов.

**Словари живут в базе, а не в коде.** Сокращения, стоп-слова и правила
категоризации пополняются без пересборки, в том числе пользователем.
Словоформы схлопывает стеммер.

**Правила категоризации задаются словами, а не основами**, и сравниваются
точно. Короткое правило не ищется по префиксу: иначе «вино» цепляется к
«винограду», а «ром» — к «ромашковому чаю».

Приоритет отражает силу признака:

| Вес | Признак | Пример |
|---|---|---|
| 45 | развод омонимов | «печень трески» против «печенья» |
| 40 | готовое изделие | конфеты, шницель, пельмени |
| 35 | для кого товар | корм для кошек, детское питание |
| 30 | конкретный товар | сосиски, креветки, такси |
| 20 | обычный товар | молоко, картофель |
| 10 | состав и вкус | молочный, сливочный, вишня |

Без этой шкалы «конфеты птичье молоко» уезжают в молочное, «шницель с сыром» —
следом за ними, а «чипсы со вкусом краба» — в рыбу. Отдельная беда — омонимия
основ: стеммер сводит «печенье» и «печень» к одному «печен», а «мороженое»
совпадает с «варено-морожеными» креветками. Такие пары разводятся только
словосочетаниями.

**Категория, проставленная словарём, пересматривается при каждом запуске.**
Словарь пополняется, и товар, однажды опознанный неверно, иначе остался бы
с этой категорией навсегда. Выбор человека при этом неприкосновенен: источник
категории хранится рядом с ней.

**Ключи товаров пересчитываются при изменении словаря.** Канон — величина
вычисляемая: добавили сокращение, и та же строка чека даёт другой ключ. При
старте товары со старой версией словаря перебираются заново по сырым
написаниям из чеков, а совпавшие записи сливаются с переносом истории покупок.

**Дедупликация чеков — частичным уникальным индексом в базе,** который не
мешает двум одинаковым ручным тратам за день.

**Кэш алиасов — в памяти процесса, а не в Redis.** Справочник семьи — сотни
записей, источник истины остаётся в базе, и рестарт ничего не теряет. Redis
понадобится, когда инстансов станет больше одного.

**Монолит, а не микросервисы.** Один разработчик, один продукт, десятки чеков
в день — ни независимого деплоя, ни независимого масштабирования здесь нет.
Границы между пакетами проведены так, чтобы выделить сервис можно было за
вечер; ближайший кандидат — обогащение чеков.

## Тесты и точность

Юнит-тесты покрывают ядро: разбор денег и количеств, парсер фискальной строки,
нормализацию названий, расчёт индекса, сборку сообщений. Репозитории
проверяются на настоящем PostgreSQL в testcontainers — заглушка не проверит ни
частичный уникальный индекс, ни `ON CONFLICT`, ни триграммный поиск.

```bash
make test              # всё
go test ./... -short   # только юнит-тесты, без Docker
```

Точность категоризации меряется на 222 размеченных строках чеков из
`testdata/*.csv` и закреплена тестом с порогом: если правка словаря ломает уже
работавшее, тест падает. Наборы разные по назначению: основной, два
проверочных и `receipt_lines_real.csv` — строки из настоящих чеков, на которых
всплывали самые неочевидные случаи. Инструмент для ручного замера:

```bash
go run ./cmd/coverage testdata/receipt_lines.csv
```

Наборы пополняются строками из настоящих чеков — именно так словарь и
дорабатывается.

Отдельно словарь проверяется на **стороннем источнике**: названия российских
товаров из Open Food Facts с их собственной таксономией, сопоставленной с
нашими категориями. Это честная проверка — ни названия, ни разметка не наши:

```bash
python3 scripts/fetch_openfoodfacts.py > datasets/openfoodfacts_ru.csv
go run ./cmd/coverage datasets/openfoodfacts_ru.csv
```

На 265 товарах точность **95%**. Оставшиеся расхождения — в основном разница
таксономий: Open Food Facts относит сухарики к выпечке, а мы к снекам; часть
названий не опознаётся в принципе, потому что не содержит признаков товара
(«Гранатовый сезон» — это сок, но по названию не скажешь).

Данные в репозиторий не кладутся: у Open Food Facts лицензия ODbL со
share-alike, и проект обязан работать без них.

## Эксплуатация

- `GET /healthz` — процесс жив;
- `GET /readyz` — база отвечает и Telegram на связи;
- `GET /metrics` — счётчики Prometheus: сохранённые траты по источнику,
  повторные чеки, нераспознанные снимки, ошибки обработчиков.

Запросы к базе идут с таймаутом и отменяются при остановке. Частота сообщений
от одного пользователя ограничена, одновременных распознаваний QR — не больше
двух: обработка снимка идёт в три прохода и заметно нагружает процессор.

Готовность проверяет обе зависимости. Связь с Telegram подтверждается фоновым
опросом раз в минуту: без этого `readyz` оставался зелёным при упавшем прокси —
база отвечает, а бот сообщений не получает.

### Замеры

На машине с 4 ядрами, `go test -bench`:

| Операция | Время | Пропускная способность |
|---|---|---|
| разбор строки QR | 1,3 мкс | — |
| нормализация названия | 34 мкс | — |
| категоризация (700 правил) | 21 мкс | — |
| распознавание QR со снимка 1024² | 12 мс | ~80/с на ядро |
| снимок без кода (три прохода впустую) | 61 мс | ~16/с на ядро |
| сохранение чека с 12 позициями | 1,1 мс | ~900/с |
| отчёт по категориям | 2,3 мс | ~430/с |
| отчёт под конкурентной нагрузкой | 1,1 мс | ~900/с |

Узкое место — распознавание снимка, поэтому оно и ограничено семафором.
База не является ограничением: запросы отчёта масштабируются по ядрам.

Потребление в покое: 23 МБ памяти, 9 потоков, 9 дескрипторов. Запуск до
готовности — 0,5 с, остановка — 15 мс.

### Поведение при отказах

Проверено на работающем сервисе:

| Отказ | Поведение |
|---|---|
| остановлен PostgreSQL | `healthz` 200, `readyz` 503, процесс жив |
| PostgreSQL вернулся | `readyz` 200 сам, пул переподключается, перезапуск не нужен |
| остановлен прокси | процесс жив, через 5 минут молчания `readyz` краснеет |
| `kill -9` процесса | systemd поднимает за ~10 с |
| `systemctl stop` | завершение за 15 мс, соединения закрыты |

## Планы

- распознавание фото чека, когда сервис не знает чек;
- разложение изменения расходов на цену, объём и смену магазина;
- лимиты по категориям и еженедельная сводка с графиком;
- магазин для чеков из QR: в фискальной строке его нет.
